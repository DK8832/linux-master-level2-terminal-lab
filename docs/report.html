02 · TROUBLESHOOTING

겉보기 성공을 다시 의심하다

첫 실행 문제
GitHub Actions가 success로 표시됐지만 로그 끝에 $'\r': command not found가 있었다. PowerShell 출력 뒤의 CR이 Bash 파일 끝에 들어갔고, bash ... | tee 파이프는 tee의 종료 코드만 반환해 오류를 숨겼다.
수정
Bash 파일을 LF로 다시 올리고 워크플로 실행 블록에 set -o pipefail을 추가했다. 이제 Bash가 실패하면 tee가 성공해도 전체 단계가 실패한다.

수정 후 실제 출력

=== LAB 01: ENVIRONMENT === KERNEL=Linux CHECK PASS | kernel is Linux === LAB 03: PERMISSIONS === MODE=755 permission-ok CHECK PASS | script mode is 755 === LAB 04: TEXT PIPELINE === ERROR_COUNT=2 UNIQUE_USERS=3 === LAB 05: ARCHIVE === ARCHIVE_SHA256=eb642b6f...bfb1295f8 CHECKS_PASSED=8 LAB_STATUS=PASS

추가 문제 해결

ps | head는 pipefail 환경에서 SIGPIPE가 생길 수 있어 표시용 파이프에만 예외를 두었다. 실제 평가 항목은 check 함수가 별도로 검사한다. 권한 역시 ls -l 모양만 보지 않고 stat -c '%a'와 test -x를 함께 사용했다.

배운 점

명령을 외우는 것보다 ‘실행 → 상태 변화 → 다른 명령으로 검증’의 세 단계가 중요했다. 또한 CI의 초록 표시만 믿지 않고 로그를 읽어야 숨은 오류를 찾을 수 있고, 파이프라인 종료 코드까지 설계해야 검증이 신뢰할 수 있다는 점을 배웠다.
